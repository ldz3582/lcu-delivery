## 2. 三阶段路线图

### 阶段 A：体验版（今天 ~ 1 天，能拉 50~200 人用）

微信体验版**不需要审核、不需要备案、不需要域名**，用 `https://` 的公网地址即可（用云托管/CDN 或临时 HTTPS）。

| 步骤 | 命令 / 操作 | 谁做 |
| --- | --- | --- |
| A1 | 微信后台「小程序代码上传」生成 `private.wx.key` + 填本机公网 IP 白名单 | 你 |
| A2 | `./ops/publish-wechat.sh build https://你的临时HTTPS地址` | 我 |
| A3 | `./ops/publish-wechat.sh upload ~/private.wx.key 1.0.0 "体验版"` | 我 |
| A4 | 微信后台 → 版本管理 → 设为体验版 → 加 500 人体验成员（上限 200 人/次，可分批） | 你 |
| A5 | 下发体验二维码 | 我 |

> 体验版限制：只能扫码、搜不到、最多 200 人（可分次），支付仍要真实商户号才能收钱。
> 想收钱就必须进阶段 B — 支付宝/微信都不允许「体验版收款」。

### 阶段 B：正式上线准备（并行 2~4 周，主要是等备案）

| 事项 | 具体动作 | 耗时 |
| --- | --- | --- |

| B2 备案 | 阿里云「ICP 备案」控制台提交：主体信息 + 网站信息 + 法人核验。**服务器在上海 → 必须备案到阿里云** | 7~20 天 |

## 3. 500 人够不够用？——容量评估

### 3.1 真实负载估算

| 指标 | 估算 | 依据 |
| --- | --- | --- |
| 日活 | 500 | 目标 |
| 人均下单 | 1~1.5 单/天 | 校园外卖典型 |
| 日订单 | 500~750 单 | — |
| 峰值时段 | 11:30–13:00、17:00–19:00 | 占全天 70% |
| 峰值下单 | ~0.1 单/秒 | 500 单集中在 2 小时 |
| 接口峰值 QPS | **30~50** | 高峰 100~150 人同时刷首页/菜单 |
| 轮询压力 | **~12 QPS** | 订单详情 5 秒轮询，60 单在途 = 12 次/秒 |
| 并发写 | 极低 | 下单是低频离散动作 |

### 3.2 当前机器能不能扛

| 资源 | 现在 | 500 日活够不够 |
| --- | --- | --- |
| CPU 2 vCPU | 峰值 5% | ✅ 够（估算峰值 <30%） |
| 内存 1.8G（JVM 480M + MySQL 128M buffer pool） | 用 853M | ⚠️ 勉强，**buffer pool 太小会拖慢查询** |
| MySQL 连接池 20 | — | ✅ 够（QPS 50 以内） |
| 磁盘 40G | 用 8.7G | ✅ 够（图片注意别爆） |
| 单点故障 | 无备份、无监控 | ❌ 这是真风险 |

**结论**：500 日活的**计算能力够**，但 2G 内存 + 单机 + 无备份属于「赌运气」。上线前必须做：

- ✅ 每日自动备份（mysqldump → 保留 30 天）— **我来做**
- ✅ 基础监控告警（磁盘、内存、容器健康）— **我来做**
- ✅ Nginx 层限流（防刷接口）— **我来做**
- 🔶 建议升到 **2C4G**（约每月多几十块），MySQL buffer pool 提到 512M，JVM 提到 1G — 性价比最高的一步

### 3.3 扩容路线（按需，不用一步到位）

| 日活 | 配置 | 成本档 |
| --- | --- | --- |
| ≤500 | 2C2G 单机（现状）+ 备份监控 | 已有 |
| 500~2000 | 2C4G 单机 + buffer pool 512M + JVM 1G | 小 |
| 2000~5000 | 4C8G + MySQL 独立上云 RDS + Redis 云版 | 中 |
| >5000 | 应用多副本 + SLB + RDS 高可用 | 大 |
